# Стандарт коммит-сообщений

На проекте используется стандарт **Conventional Commits**. Это необходимо для автоматической генерации ченджлогов (Changelog) и поддержки чистоты истории Git.

## Структура сообщения

```text
<тип>(<область>): [<номер-задачи>] <краткое описание>

[необязательное тело коммита с подробностями]
```

### 1. Типы (Types)
* `feat` — Новый функционал (новая фича).
* `fix` — Исправление бага.
* `refactor` — Изменение кода, которое не исправляет баг и не добавляет фичу (улучшение структуры).
* `chore` — Обновление задач сборки, настроек IDE, зависимостей (нет изменений в production-коде).
* `docs` — Изменения только в документации.
* `style` — Правки форматирования, отступов, точек с запятой (без влияния на логику).
* `test` — Добавление или исправление тестов.

### 2. Область (Scope)
Область пишется в круглых скобках. Это **существительное**, обозначающее затронутый модуль системы.
* Примеры: `(auth)`, `(report)`, `(api)`, `(db)`, `(ui)`.
* Если коммит глобальный (затрагивает всё), область можно опустить: `feat: [NV-92] глобальное изменение`.

### 3. Номер задачи (Task ID)
Всегда указывайте ID задачи из трекера (например, `[NV-92]`) сразу после двоеточия или внутри описания, если это настроено в CI/CD.

## Примеры

**Правильно:**
* `feat(report): [NV-92] add app.report module`
* `fix(auth): [NV-105] fix blank screen on failed login`
* `chore: update phpunit dependency`

**Неправильно:**
* `fixed bug` (нет типа, нет скоупа, нет задачи)
* `feat(NV-92): add code` (номер задачи засунут в скоуп вместо модуля)
* `refactor: сделал красиво` (описание должно быть на английском, если это принято в команде)
